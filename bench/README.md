# Render benchmark: stock UI vs xterm-ui

`render-benchmark.mjs` compares the *output-rendering* cost of the stock UI
(DOM/HTML via `setupOutputMessageHandler` / `AnsiAwareBuffer.toDom()`) against
`xterm-ui` (`AnsiAwareBuffer.toAnsi()` written into `xterm.js`).

Both UIs run the same `Client` + `registerScripts` core (see
`docs/CLIENT_UI_DECOUPLING.md`) — triggers, GMCP parsing, and game state are
identical either way. This benchmark deliberately isolates the render layer by
injecting synthetic `message` events directly, rather than replaying a real
telnet session, so the numbers reflect rendering cost specifically, not
trigger/parse cost (which doesn't differ between the two UIs).

## Run it

```
yarn bench:render                                  # spawns vite dev automatically
BENCH_RUNS=8 yarn bench:render                      # more runs = more stable medians (default 5)
BENCH_BASE_URL=http://localhost:5173 yarn bench:render  # point at an already-running dev server
```

Results print as a table and are written in full (every raw run, not just the
median) to `bench/render-benchmark-results.json`.

## How injection works

The script drives real Chromium via Playwright and, on each target page,
dynamically imports the exact module URLs the app itself imports
(`/src/modules/core/eventBus.ts`, `/src/client/ansi/FormatState.ts`). The
browser's ES module cache resolves that to the *same* `eventBus` singleton
already wired up to the running UI — no debug hooks or product code changes
needed. It then calls `eventBus.emit('message', new AnsiAwareBuffer(line),
type)`, the same call `mudClient` makes when real server text arrives.

The corpus is generated by a seeded PRNG (`mulberry32`), so the exact same
"incoming data" replays on every run and for both UIs — line lengths, ANSI
segment counts, and colors are fixed given a seed, only the wall-clock/CDP
measurements vary run to run.

## Scenarios

- **burst-empty**: 300 messages emitted in one synchronous burst (e.g. an AoE
  fight landing at once) on an empty scrollback.
- **burst-longscroll**: same burst, but preceded by 3000 prefill lines, so it
  measures append/trim cost once the scrollback already holds a long session.
- **steady-30-per-sec**: the same 300 messages paced at ~30/sec — closer to a
  sustained fast-combat rate than an instantaneous burst. Wall-clock time here
  is dominated by the deliberate pacing sleep (~10s minimum); the meaningful
  signal is `scriptMs`/`layoutMs`/`recalcStyleMs`, not `totalMs`.

## Columns

| Column | Source | Meaning |
|---|---|---|
| `totalMs` | `performance.now()` in-page | Time from first `emit` to two settled `requestAnimationFrame`s after the last one. |
| `emitMs` | `performance.now()` in-page | Time spent in the emission loop itself (script time for calling `emit` + any synchronous listener work + pacing sleeps). |
| `scriptMs` / `layoutMs` / `recalcStyleMs` | CDP `Performance.getMetrics()` delta | Cumulative main-thread time attributed to script execution / layout / style recalc during the run. These are the numbers to trust for "how expensive is rendering," since they're independent of pacing sleeps. |
| `layoutCount` | CDP | Number of layout passes forced during the run — a proxy for how much the DOM/canvas is being reflowed. |
| `longtasks` / `longtaskMs` | `PerformanceObserver('longtask')` | Count and total duration of >50ms main-thread tasks — a direct jank indicator (each one is a frame the user would visibly feel). |
| `heapDeltaMb` | CDP `JSHeapUsedSize` delta | JS heap growth over the run. **Noisy** — GC can fire mid-run and show as negative growth. Read directionally over several runs, not as a precise number. |

## Caveats

- **Different scrollback caps by design**: stock trims to
  `Ustawienia > outputMaxElements` (default 1000 DOM nodes); `xterm-ui` was
  spiked with a 5000-line xterm scrollback. This wasn't normalized, so
  `burst-longscroll` isn't an apples-to-apples buffer size — it's each UI at
  its own real-world default.
- **Headless, single-process Chromium**: absolute numbers will differ from a
  real user's machine/browser. Use this to compare the two UIs against each
  other on the same run, not as an absolute performance budget.
- **No network fetches are mocked**: feature-script data loads (herbs,
  magics, knowledge, etc.) fail fast in an offline sandbox; the harness waits
  1.5s after page load before measuring to let that settle, but on a
  network-connected machine those fetches may still be in flight when
  measurement starts — increase the settle wait if you see it in results.
